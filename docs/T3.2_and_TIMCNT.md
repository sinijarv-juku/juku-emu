# T3.2 and TIMCNT

The clock of PIT #3 counter 2 (T3.2, D57) is unsettled. RomBios builds its
TIMCNT stopwatch on T3.2, and that works only if T3.2 is clocked once per
frame. The RDEM demo builds its random numbers from T3.2, and that works only
if T3.2 runs fast. No single wiring satisfies both.

"MD §n" refers to `Juku_machine_description.md`. Addresses are from
`resources/roms/ekta37.bin` (RomBios 3.43m); `ekta31.bin` has the same code
at the same addresses, and `jmon33.bin` has it at 0057–006F and 32BB.

## The hardware

T3.2 is counter 2 of the third КР580ВИ53 (D57): port 1Ah, control word at
1Bh. Two sources disagree about its clock:

- **The 1987 schematic** (sheet 2) draws CLK2 on bus line 13, "1,23M", the
  same line as T3.0's CLK0. D103, a К555ИЕ10, divides the 16 MHz crystal by
  13 to make it. G2 is tied high, and OUT2 leaves as "SYNC B.", the tape
  transmit clock of that early board (MD §10.2).
- **MAME** clocks T3.2 from VER RTR, once per frame (49.92 Hz):
  `m_pit[1]->out_handler<1>().append(m_pit[2], FUNC(pit8253_device::write_clk2)); // ~49.92 Hz`.
  It gives no reason.

There is no schematic of the production board.

## What RomBios 3.43m does with T3.2

**At start-up.**
- ROM 01FC–020C writes the control word B0h (counter 2, LSB then MSB,
  mode 0), then the count FFFFh.
- ROM 02CC clears the stopwatch at D463h.

**On every frame interrupt.** ROM 04A7 calls 053D:

```
053D  LHLD D463           ; stopwatch so far
0540  MVI A,80 / OUT 1B   ; latch counter 2
0544  IN 1A / CMA / MOV E,A   ; low byte, inverted
0548  IN 1A / CMA / MOV D,A   ; high byte, inverted
054C  DAD D               ; add ~count
054D  MVI A,FE / OUT 1A
0551  INR A / OUT 1A      ; reload FFFEh
0554  SHLD D463
```

In mode 0 a newly written count goes into the counter on the next clock
pulse, and that pulse does not count down. After the reload, the first pulse
loads FFFEh and every later pulse takes one off. The inverted value,
FFFFh − count, is therefore the number of pulses since the reload, including
the one that loaded it. The handler adds that number to D463h and starts the
next count.

**TIMCNT** (entry FFA1h) dispatches to ROM 16A6, which jumps to 057A:
- E = 0 clears D463h;
- E = FFh returns D463h in DE.

The same code also handles INTCNT (FF9Eh, the one-shot timer at D45Eh). INTCNT
takes one off per interrupt in software; only TIMCNT reads the hardware.

## With T3.2 on the frame clock

- **Normal case.** Each frame, the edge that triggers the interrupt also
  loads FFFEh, the handler reads ~FFFEh = 1, and TIMCNT goes up by 1. That is
  the manual's "20 ms units" (MD §14.2). The emulator, wired this way,
  measures 50 per second at the monitor prompt.
- **Why read the hardware.** The disk BIOS shuts the frame interrupt out
  for every transfer:
  - ROM 2746 masks level 5 through FF7Ah and executes DI; ROM 2751 unmasks
    it and executes EI.
  - The read, read-track and write-track routines (2581, 26DC, 2711) call
    them around the command and the IN/OUT 1Fh loop, which waits for the
    sector to come round.
  - A sector read can therefore keep interrupts off for up to a revolution,
    200 ms or 10 frames. A whole track takes at least a revolution.

  The 8259 holds only one pending request, so a counter kept in software
  would lose about ten ticks per disk access. That is how INTCNT behaves,
  which is acceptable for a timeout. On the frame clock, T3.2 keeps counting
  frames while the CPU is not listening, and the next interrupt adds them
  all, so the stopwatch loses no time. With T3.2 at 1.23 MHz, reading the
  counter would gain nothing.

Programs on period disk images rely on these units:

| Program | Use of TIMCNT |
|---|---|
| PUSHER | `delay(n)` waits until TIMCNT ≥ n × 50; called with 1–3 after messages such as "Tasemete fail puudub !" |
| LOGER | waits until TIMCNT ≥ 150 (3 s) |
| AVTEST | `delay(n)` waits until TIMCNT ≥ n × 20 |
| LAOLEO | shows minutes:seconds from TIMCNT / 50 mod 60 and TIMCNT mod 3000 |
| LAND, NIELS, 9.COM, AEG, ARVUTA | reset it and read it back in loops |
| TETRIS, TET, XONIX | use its low bits as a random seed |

The images are JUKGAME1, J3KGAME1, M2 and M5 (flux dumps from a private
collection), Juku_9 `003_ok.cpm` and the Kryoflux dumps, in the document
archive outside this repository. Several more programs carry the compiler runtime's TIMCNT
wrappers without calling them. RDEM is one of them.

## With T3.2 at 1.2308 MHz

- **How much it adds.** A frame is 40,064 CPU cycles, 24,655 pulses at
  1.2308 MHz. Each interrupt adds about that much, less the few pulses
  between the latch and the reload.
- **The values it shows.** The 16-bit stopwatch only changes when an
  interrupt runs. It steps 0 → 24,655 → 49,310 → 8,429 (wrapped) → …,
  wrapping about every 53 ms. One emulated second at the prompt added 50,621,
  which is 1,232,750 wrapped to 16 bits.
- **Effect on the programs.**
  - A wait for TIMCNT ≥ N with N below about 24,000 ends at the first
    interrupt. PUSHER's 3-second message pause and LOGER's 3-second wait
    become about 20 ms.
  - LAOLEO's clock shows nonsense.
  - The random seeds still work.
- **The ROM was not designed for this.** A stopwatch that wraps every 53 ms
  and changes only every 20 ms has no use. The FFFEh reload, which makes each
  frame add exactly 1, only makes sense with a slow clock.

## What RDEM needs

RDEM.COM is on the JUKPROG1 and JUKU1 disks and on several Kryoflux dumps.
Its title screen sprinkles random pixels around the JUKU logo, and it is
remembered working that way on school machines.

**How it makes random numbers.** The routine at 018F builds each number from
bit 1 of port 1Ah, read nine times in a row (the IN at 01D3):
- It never programs T3.2 and never latches it, so the reads alternate between
  the low and the high byte.
- It needs that bit to change between reads a few hundred microseconds apart,
  which takes a fast clock.

**What it sees on the frame clock.** The counter always holds FFFEh when RDEM
reads it, because each frame's interrupt reloads it before it can count down.
RDEM sees only FEh and FFh, and bit 1 is set in both. Every number comes out
as 511, and the routine's mixing step then alternates between two values. The
screen shows two pixels above the logo.

**A side effect on TIMCNT.** RDEM's odd number of reads leaves the counter's
byte flip-flop at the high byte. The interrupt handler then reads the bytes
swapped and adds 256 instead of 1 on some frames. In the emulator TIMCNT ran
at about 100 per frame while RDEM was running.

**On the 1.23 MHz clock** the bits vary, and the logo is sprinkled with
random pixels. With the 8253 emulated as it is, about 100 lie below the logo
8 s after it starts.

## The conflict

| T3.2 clock | TIMCNT and the timing programs | RDEM |
|---|---|---|
| Frame (MAME) | work | two pixels |
| 1.2308 MHz (schematic) | broken | works |

Both kinds of program are Estonian software from the period, so the most
likely explanation is that both kinds of board existed:
- **Frame clock.** RomBios 3.43m and the TIMCNT programs fit a board with
  T3.2 on the frame clock.
- **1.23 MHz clock.** RDEM and the 1987 schematic fit a board with T3.2 on
  1.23 MHz. Such a board probably ran a ROM whose TIMCNT does not read T3.2.
  No such ROM is at hand.

**Ruled out: the timer chip.** The КР580ВИ53 is described as a copy of the
8253. The differences reported from tests on real chips (some without a latch
register, glitchy unlatched reads while a counter changes, mode 1 loading only
on a gate edge) do not make a counter that never changes give varying reads.

**Ruled out: a missing count.** An earlier idea, that RomBios writes no count
to T3.2 and that the 8253 keeps counting with no count written, was wrong. The
ROM writes FFFFh at start-up and FFFEh every frame.

## In the emulator

The clock is an option, with the frame clock as the default:
- **Core.** `Machine::set_t32_fast_clock` and `juku_set_t32_fast_clock`
  choose it (spec §4.5). The switch takes effect at once and survives resets
  and snapshot loads.
- **Settings.** On both front-ends it is the Clock at 1.23 MHz checkbox in
  the Machine pane, under Timer T3.2 (`T32FastClock`).
- **Tests.** `core/tests/t32_clock.rs` checks TIMCNT on both clocks, and
  RDEM on both clocks when the test disks are at hand.
